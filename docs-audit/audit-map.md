## 1. BROKEN

Ordered by what it costs the user. Each has an executed reproduction; latency marked.

1. **No volume anomaly on a still-emitting scope can ever alert.** `_get_latest_active_anomalies` keeps a scope only when `anomaly_bucket >= max(EventMetric.bucket)` (`signals.py:255-264` × `:142`), but ingestion settling holds emission `settling_buckets` behind the collected head (`anomaly_detector.py:700` `_emission_end`, `tasks.py:785`) — so the predicate is satisfiable only by scopes that went to zero. Live: 233 open signals, `Counter(state)={'recent':233}`, zero `latest_scan`; 192k anomalies detected / 20 alerts queued; all 16 event-scope items ever delivered have `actual_count` 0.0 or 1.0. **Fix:** classify against the settled head (`max(bucket) - settling_buckets`), i.e. compare the anomaly bucket to the same `emission_end` the detector used, not to the raw metric head. *(FIRING)*
2. **One inbox action silences every other scope of the same rule+direction, indefinitely.** `_correlation_group_id = uuid5(scan_config : rule : direction)` has no scope component (`dispatch.py:54-75`), and `_SUPPRESSING_INBOX_STATUSES` gates the whole group (`:82`, `:358-363`); the only release path, `_reopen_closed_incidents` (`:274`), needs *every* scope closed — which the suppressed scope itself prevents. Controlled arms: identical data, 21 hourly ticks, no ack → new scope delivers every tick; with ack → 1 delivery total, forever. Live group `bd6c96f5` covers 7 unrelated scopes with an operator note from 2026-07-30. **Fix:** add `scope_type:scope_ref` to the group key (direction/rule keying already works). *(FIRING)*
3. **Catalog metrics are evaluated on the scan config's grid, not their own.** `anomaly_evaluation_start = min(time_from, time_to - delta*30)` uses the scan's `delta` (1h) and is passed verbatim into `_recalculate_project_metric_anomalies` (`tasks.py:782-786` → `detect.py:859-868`), so a 1d metric gets a 30-hour window ⇒ 0–1 candidate buckets, and the only candidate is always the one settling withholds. Control: a healthy synthetic 1d metric with a genuine 25-day collapse → 264 anomalies under a 1d config, **0** under a 1h config. Live: rd1 has read 0.0 for 3 days, `latest_signal: null`, forecast locked to 0.0/0.0. **Fix:** derive `evaluation_start` from the metric's own `interval_spec.delta` inside `_recalculate_project_metric_anomalies`. *(FIRING)*
4. **`min_prev_share=0.001` hides regressions of the same magnitude it reports.** `release_regression.py:41`/`:325` gates on a share of the baseline release — the exact mistake today's comparability rewrite removed from the gate — and on the 2488-event catalog it is ~496× stricter than `min_expected`, excluding 145 of 264 evidenced scopes. Bit-exact reconstruction of the shipped model reproduces the persisted row character-for-character, then yields `auth:close:auth` and `spot:open:wind` (ratios 0.48/0.40, indistinguishable from the two that shipped); forcing `search:result:search` to zero produces **no** row at all. A live `missing` row (`:open:detailed_forecast`, 65→0) is suppressed today. **Fix:** delete the share floor; `min_expected` is the evidence gate. *(FIRING)*
5. **Release-regression alerts print a sparkline from a different series, scale and window than the numbers above it.** `anomaly_context.py:143-157` falls to the generic else-branch and reads `scope_ref` as an event id, so the trend is the event's *all-versions* 24h volume while the line above is a release-cohort aggregate over a 31h window. Reconstructed `build_sparkline()` matches the shipped glyphs byte-for-byte on the newest delivery (963557bf); `d4d8cf9e` shows a glyph rising to the series max under a "dropped 51.9%" headline. `_build_ai_explanation` already omits it for this scope type; the human template does not. **Fix:** omit `${sparkline_line}` for `release_regression` (or plot the cohort from `EventMetricBreakdown`). *(FIRING, every delivery)*
6. **A withheld comparison renders as the affirmative "No events regressed in the latest release."** `comparable`/`emerging_share` are computed, logged at INFO (`regression.py:156-173`) and discarded — no column, no schema field (`ReleaseRegressionsResponse` = `app_version_column, items, latest_version, scan_config_id`), and `release-regression-panel.tsx:89-92` prints the affirmative on an empty list. Suppressed and healthy payloads are byte-identical (`payload A == payload B: True`). Same file's docstring states the opposite intent. Two paths (`:280`, `:298`) also return the dataclass default `comparable=True` when no comparison happened. **Fix:** carry the verdict onto the row/response and render "cannot be judged yet"; make the no-comparison paths return `comparable=False`. *(FIRING whenever the gate engages)*
7. **Seasonal phase is keyed on list index, not on the bucket's position on the time grid.** `expand_series` drops uncovered buckets from the list (`anomaly_detector.py:183`) and `_present_series` drops absent ones (`:680-697`), while `_seasonal_factors`/`_phase_anomaly_at`/`_detect_trend_shift` select partners by `j % period == idx % period` (`:430`, `:467`). On **real windy-ios data with real live settings**, deleting one bucket turns 0 anomalies into 2 false spikes (08-02 05:00 z=+4.7, 08-03 05:00 z=+4.3), stable across five hole positions; the contaminated expectation is drawn from the adjacent hour. Armed by one failed hourly collection or one absent day on a 1d metric. **Fix:** index phase by `(bucket - origin)//delta`, not by list position. *(LATENT — grid is currently contiguous 816/816)*
8. **A metrics replay deletes correct anomalies at the head of the replayed window and never restores them.** `collect_metrics` passes the live settling allowance to replays too (`tasks.py:783-800`, no `is_replay` branch though `is_replay` is in scope at `:469`); `_replace_scope_anomalies` deletes all of `[start, end)` (`detect.py:164-174`) and reinserts only up to `emission_end`. End-to-end with real models: replay loses `08-01 16:00`/`17:00`, `settling_delay=0` loses nothing, next scheduled run does not restore. `NO_INGESTION_SETTLING` exists for exactly this (`detect.py:54-59`). One prod replay did wipe two buckets and self-healed only because the next collection's 30-bucket trailing window still covered them. **Fix:** `settling_delay = NO_INGESTION_SETTLING if is_replay else ...`. *(ARMED — one replay observed; permanent loss needs a replay ending >30 buckets back)*
9. **Prerelease/TestFlight builds are eligible as regression subject *and* baseline.** `release_regression.py:283` calls `order_versions(activations.keys())` with no `released_versions`/`is_prerelease_version` filter; `grep -c prerelease` = 0 in both `release_regression.py` and `regression.py`, so `ScanConfig.app_version_prerelease_pattern` is a silent no-op there. Demonstrated: same data → chart says `latest_version=15.7.4`, regression says `15.8.0-beta.1`, emitting a `missing` row (the kind the comparability gate deliberately passes through); and with the beta as *baseline*, a false `volume_drop` at `emerging_share=0.0`, which no gate catches. `anomaly-detection.md:214` documents the opposite. **Fix:** run activations through `released_versions()` before `order_versions`. *(LATENT — no prerelease tag on live data)*
10. **Telegram messages have no length cap, and the resulting failure loops forever.** `_build_items_text` (`alerts_messages.py:228-256`) iterates all items with no slice; `dispatch.py` has no chunking or ceiling. Rendered against live field values: 14 items = 4154 chars > Telegram's 4096 → HTTP 400. `_is_telegram_markdown_parse_error` returns False for "message is too long", and the fallback is gated on `message_format == telegram_markdownv2` while the live rule is `plain`, so it raises. `last_notified_at` is written only on success (`alerts.py:573`), and `dispatch.py:311` short-circuits on `is None` → the same oversized delivery is rebuilt and fails every scan. Worst live bucket: 96 co-firing scopes. **Fix:** cap items in the rendered body with "+N more"; stamp/skip on permanent failure. *(LATENT — largest real delivery is 5 items / 2420 chars)*
11. **Accept on a contract-violation drift changes nothing yet mutes the check permanently.** `_apply_acceptance_to_plan` handles only `new_field`/`type_changed`/`missing_field` and returns False for `enum_violation`/`required_null_violation`/`regex_violation`/`range_violation` (`schema_drift_service.py:120-152`), while `apply_drift_action` sets `status='accepted'` regardless (`:217`); the UI offers the same Accept button for all types (`EventDriftBadge.tsx:160`, gated only on status). Measured: badge 1→0, alert candidates 1→0, field snapshot unchanged; because the contract was never widened, the violation re-fires every scan and refreshes `detected_at`, so the row never reaches the 30-day cutoff. Contrast: accepting a `new_field` makes the diff stop producing it. **Fix:** refuse accept for the four contract types (or make it widen `enum_options`/`contract_max_bad_rate`). *(LATENT — 0 of 27 live field definitions have contracts)*

## 2. NOISE

Works as written; erodes the trust needed to act on a 3am page.

- **Onset leaks ~21 `phase` rows where the design intends one `trend` row.** On a sharply peaked daily shape the run-collapse fires per-bucket before the trend anchor claims the run (the repo test gets 1 row on a smoother shape). *Change:* let `_detect_trend_shift` claim the buckets from the run's first bucket rather than only when the run start is inside the window. *Cost:* onset detection latency of roughly one cycle on peaked series.
- **A week-old death is re-announced as fresh rows.** Row count is non-monotone: 28 rows at 48h → 0 at 72–96h → 28 again at 120–168h, because the STL trend decays under `min_expected_count` and `_detect_trend_shift` stops claiming the buckets (`anomaly_detector.py:558-560`), so phase rows resurface at z=-20. *Change:* make suppression depend on the persisted incident anchor, not on the live trend level. *Cost:* none in signal; a genuinely *new* death at a decayed level would need the anchor check to distinguish it.
- **The Anomalies page is 92% one legacy scan.** "Old events (iOS)" supplies 79–95% of open event-scope signals — a denominator effect (2059 of 2496 events, per-scope firing rate 8.8% vs the live scan's 12.8%), not bad detection, but a reader cannot find the live-stream signal. `AnomaliesPage.tsx` has a magnitude filter and no scan filter. *Change:* add a scan/event-type facet. *Cost:* zero signal; pure list composition.
- **Metric-scope alerts burst at incident open.** `_project_metric_state_config_id` anchors `AlertRuleState` on the min-id config while `AlertDelivery.scan_config_id` is the dispatching config (`dispatch.py:288-290` × `alerts.py:563-574`), so each non-canonical config that dispatches before the canonical one in the first cycle emits one extra delivery (≤N-1 = 2 here) before converging to one per cooldown. *Change:* look the state up by the same canonical id the dispatcher used. *Cost:* none. Related, unfired: `_project_metric_state_config_id` takes `min()` without filtering on `interval`/`time_column`, which the scheduler requires — if a project's lowest-id config lacked either, the state would anchor to a config that never dispatches and the burst would become permanent. All 8 live configs are `interval=1h`.
- **Release-regression alert items state no window.** The item carries a single hourly `bucket` (e.g. `2026-08-04T06:00Z`) while the finding spans `window_from`→`window_to` (31h). A reader reasonably reads "actual=21807" as an hourly count. *Change:* render the window. *Cost:* none.
- **Hour-of-week phase runs on 3–5 cycles.** `_select_phase_period` always picks 168 once 3 weeks exist; the robust scale from 5 same-phase points is narrow, so a 4σ call there is materially more sensitive than the same number at 9 cycles (expectation barely moves: 51.16 vs 55.69). The "Baseline Window" field (`MonitoringTab.tsx:179-186`) has no help text and does not govern this. *Change:* widen the phase history floor or expose it. *Cost:* a longer phase history silences borderline calls — the same bucket that fires at 5 cycles is silent at 9.
- **`/app-versions` returns a truncated tail when `from=`/`to=` are passed** (max bucket 13:00 vs 17:00 unparameterised), so hand-summing the parameterised response yields wrong totals. Observed during reconstruction, not root-caused.

## 3. NEEDS A DECISION

- **Should an incident that is still ongoing after `recent_signal_window_hours` (24h) remain an OPEN signal?** Today it is announced at onset (~3h), gets a permanent dated marker on the chart, then drops off the signal list — a five-day-old 50% traffic loss shows nothing. Re-opening the emission gate restores the per-scan flood that tripl-jfm3.46/.47 removed; the cheap levers are raising `recent_signal_window_hours` or a "still-firing" re-check against the persisted anchor row.
- **How long should a known-dead event keep generating anomaly rows, and should "still dead" be a heartbeat state rather than a per-bucket z-score?** It currently fires loudly for ~a week (22–28 rows/scan at z=-20) then goes quiet through four separately-intended mechanisms. The product already has a purpose-built surface for this — `release_regression`'s `missing` finding — which is exempted from suppression.
- **Should an accepted contract-violation drift survive a materially worse recurrence?** Accept currently acts as a permanent acknowledgment; `snooze` (7 days) is the time-boxed alternative and `reopen` the undo. A severity-aware reopen stops silent degradation but reintroduces re-nagging on a violation someone already judged.
- **Should `VariableValueDrift` put the value set in the key?** It is `UNIQUE(variable_id, event_id)` with the values as mutable payload, so an accepted pair absorbs every future novel value — unlike `SchemaDrift`, which it claims to mirror and which keys on content. Moving the key (or reopening only on values outside the resolved set) is safe for `accept` because accepted values enter `allowed_values`. Separately, the Reopen button exists on the schema-drift badge but not on the two variable-drift panels, both of which hard-filter to open/snoozed.
- **Should the "False positive" ratchet be per-scope, decaying, or confirmed?** One click raises `sigma_threshold` +0.5 and `min_expected_count` +5 project-wide, permanently; it is labelled, documented, audit-logged and undoable in Monitoring settings, and has never fired in prod (`false_positive_count=0`, still at the operator-set 4.0/50). It becomes much easier to pull once finding #2 is fixed and groups are per-scope — decide the semantics before that lands.
- **Retire the "Old events (iOS)" scan, or filter it out of the Anomalies list?** It is watching a deprecated stream the operator explicitly created a scan for, it fires at a *lower* per-scope rate than the live scan, and it has delivered real alerts — but it owns the page.
